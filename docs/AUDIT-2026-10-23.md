# LinkPay Business: security and correctness audit

**Date:** 2026-10-23. **Scope:** backend, web, admin and mobile at `88be6f2`.

**Method:**
- Six read-only review agents each took one area: auth, money movement, the public surface, admin and ops, web and admin, and mobile.
- A seventh agent checked that everything installs and builds.
- Every High and Medium item below was re-read in the code before it went in.
- **Confirmed** means the defect is visible in the code. **Plausible** means it depends on something outside the repo, usually how Liquifia behaves.

**Headline:** the codebase is careful in most places. There is no NoSQL injection, no XSS, no data shared across tenants through caching, no route with a missing permission, and webhooks are handled properly. The serious problems are a few concurrency gaps around payouts, two weak spots in sign-in, and idempotency keys being thrown away on the clients. Fix those before the first live payout.

## Re-audit (batch 8, 2026-10-25)

After batches 1–7, about 27,000 more lines, a second full review ran: five read-only reviewers, each in a clean copy of `main` at `0577e51`, covering auth, money, the public surface, the client apps, and ops. Every finding was checked against the code before it was fixed. All the fixes are on branch `fix/audit-batch-8`.

**Critical (fixed)**
- **R1: Sign-in to any passwordless account with a known string.** `login` compared against `user?.password ?? DUMMY_HASH`, and `DUMMY_HASH` hashed the literal `"dummy-password-for-timing"`. Batch 3's takeover fix makes passwordless accounts, so anyone could sign in to them with that string, which reopened H1.
  - Fixed: an account with no password never passes, and both dummy hashes now hash a random value.
  - A regression test covers it.

**Medium (all fixed)**

*Auth and sessions*
- Account deletion checked the password with no rate limit, which with a stolen token led to a PIN change. Now all signed-in password re-checks share one limit.
- The PIN lockout never escalated, and common PINs were accepted. Now there's a daily cap of 15 that only a reset clears, plus a weak-PIN list.

*Money and approvals*
- A retry was refused after a saved beneficiary was deleted, which invited a second payment. Replays are now built from the sent transfers.
- "Approve N" wasn't bound to what was shown. Now `awaitingMeKobo`, `expect`, and 409 `BATCH_CHANGED`; web and mobile show "Approve N · ₦X".

- Production could boot with console email when `NODE_ENV` was unset. `NODE_ENV` is now required, and the email guard applies with any live key.
- A non-numeric sync interval silently broke payout follow-up. Numeric env vars are now validated.
- `JWT_SECRET` was only checked for presence. Both secrets now need 32+ characters, and repo values are refused when live.
- Invoice reminders could starve platform-wide. The query now skips finished schedules.
- Staff invites outlived the inviter. They're now revoked on disable or demote, the inviter is checked on accept, and accepting is audited.

## Fix before going live (High)

### H1. Someone can take over an account before its owner verifies it (confirmed)
- **Where:** `backend/src/controllers/auth.ts:84-95` (register) and `:146-160` (`verifyLoginOtp`).
- **Defect:** Anyone can register `cfo@victim.com` with their own password. When the real owner later signs in with an email code, the account is marked verified and keeps the attacker's password.
- **Why it can't be undone:** there is no password reset or change flow, so the owner can't remove that password.
- **Fix:**
  - When an OTP verifies a never-verified account, clear its password and require a new one.
  - Add password reset and password change, and revoke every session when either is used.

### H2. The OTP attempt cap can be raced, so codes can be brute-forced (confirmed)
- **Where:** `backend/src/services/otp.ts:35-53`.
- **Defect:**
  - `attempts += 1; save()` is a read-modify-write, so a burst of parallel guesses counts as one attempt.
  - Every new code (one per 60 s) starts the count from zero.
  - An email-OTP sign-in is a full sign-in (`skipEmailFactor`). Staff 2FA uses the same code.
- **Fix:**
  - Count the attempt atomically before comparing: `findOneAndUpdate({email, purpose, attempts: {$lt: 5}}, {$inc: {attempts: 1}})`.
  - Add a daily cap per email on codes issued and verified.

### H3. A payout can be submitted twice at once, and a paid transfer can end up marked failed (plausible)
- **Where:** `backend/src/services/transfers.ts:461-510` and `:577-599`, and `backend/src/controllers/webhooks.ts:60`.
- **Defect:**
  - Nothing claims a transfer before it is sent.
  - Every `payout.*` webhook runs `processOpenTransfers()` with `minAgeMs: 0`. That skips the processor's `running` guard.
  - `lastCheckedAt` is only saved after `createPayout` returns, so a transfer that is still being sent gets picked up and submitted again.
- **Why it matters:** both copies carry the same idempotency key, which is good. But if Liquifia answers the duplicate with any 4xx other than 408, 409, 425 or 429, the second caller saves `status: "failed"`.
  - The first caller then saves `payoutId`, but `status` stays `failed`.
  - Money has left the account, the user is told the transfer failed, and the debit row stays `pending` for good.
  - If the user resends, the recipient is paid twice.
- **Fix:**
  - Claim the transfer atomically before calling Liquifia (`findOneAndUpdate({_id, status: "processing", submittingUntil: {$lt: now}}, …)`).
  - Make every status write conditional on `status: "processing"`.
  - From the second attempt on, treat a 4xx as unknown and look the payout up by `reference`.
  - Have the webhook refresh only the transfer the event names, or go through the guarded runner.
- **To confirm:** ask Liquifia what it returns for a concurrent request with the same idempotency key.

### H4. The account lock can expire while it is in use, and any holder can release it (confirmed)
- **Where:** `backend/src/services/transfers.ts:199-219`.
- **Defect:**
  - `LOCK_MS` is 15 s, but the Liquifia balance call inside the lock can take up to 30 s (`liquifia/client.ts:47`).
  - The `finally` block unsets `lockedUntil` without checking who holds it.
- **Why it matters:** two transfers can both pass the available-balance check on the same money. A Safelock that is meant to be unbreakable can end up underfunded.
- **Fix:**
  - Store a random owner token and release only with `{_id, lockToken}`.
  - Make the lock TTL much longer than the work inside it, or give the balance call a short timeout of its own.

### H5. The hold is released as soon as Liquifia accepts a payout, not when the debit lands (plausible)
- **Where:** `backend/src/services/transfers.ts:173-184` (`heldByAccount`).
- **Defect:** Once `provider.payoutId` exists, the transfer stops counting as held. The code assumes Liquifia's `GET /balance` already shows the debit by then. Nobody has checked that against live Liquifia: no live payout has been sent, and the mock debits immediately.
- **Why it matters:** if Liquifia's balance is a few seconds behind, the same money looks available twice.
- **Fix:** hold until the transfer reaches a final status (`OPEN_TRANSFER_STATUSES` already exists and isn't used), or get Liquifia to confirm when the debit happens.

### H6. Clients throw away the idempotency key exactly when it is needed (confirmed)
- **Where:**
  - Web: `web/src/components/transfers/new-transfer-dialog.tsx:149`, `bulk-transfer-dialog.tsx:151`, `savings/pocket-sheet.tsx:217` and `savings/safelock-form-dialog.tsx:108`.
  - Mobile: `mobile/src/app/(app)/(home)/savings/safelock/new.tsx:158` and `mobile/src/lib/send-draft.ts:27`.
- **Defect:** Any error except `ACCOUNT_BUSY` creates a new key. That includes `API_UNREACHABLE`, `TIMEOUT`, `NETWORK`, 5xx and `PROVIDER_ERROR`, which are exactly the cases where the server may already have done the work. On mobile, Edit then Continue always issues a new key. The app also gives up after 20 s, while the server can wait 30 s on Liquifia.
- **Why it matters:** a retry after a dropped response sends a second transfer, or locks a second Safelock that can't be broken early (up to 1,000 days).
- **Fix:**
  - Keep the key on network errors, timeouts, 5xx and provider errors.
  - Only replace it after a definite 4xx refusal or when the details actually change.
  - Raise the mobile timeout above the server's.

### H7. The staff JWT secret falls back to a value in the repo (confirmed)
- **Where:** `backend/src/config/env.ts:16` and `:32-34`.
- **Defect:** Unless `NODE_ENV` is exactly `production`, staff tokens are signed with `dev-staff-jwt-secret-not-for-production`. `bun start` doesn't set `NODE_ENV`, and the docs never say it is required.
- **Fix:**
  - Always require `STAFF_JWT_SECRET` except under `NODE_ENV=test`.
  - Refuse to start if it equals `JWT_SECRET` or is shorter than 32 bytes.

### H8. Nothing guards against live keys or console-only email in production (confirmed)
- **Where:** `backend/src/config/env.ts:47-50`, `backend/index.ts:20-30` and `backend/src/services/email.ts:24-36`.
- **Defect:**
  - `bun run dev` starts every background job (payouts, sync, reminders, risk checks, Safelock release) whether the Liquifia key is `sk_test_` or `sk_live_`. The docs say the local `.env` currently has live keys.
  - `setEmailProvider` is never called anywhere. In production, every OTP, 2FA code, team invite token and staff invite token would go to stdout and into the logs.
- **Fix:**
  - Refuse an `sk_live_` key unless `NODE_ENV=production` and `ALLOW_LIVE=1` are both set.
  - Refuse to start in production while the email provider is still the console one.

### H9. KYB approve and reject are check-then-save, and provisioning can race (confirmed)
- **Where:** `backend/src/controllers/admin.ts:31-40` and `:126-131` (and reject/changes at `:200` and `:220`), and `backend/src/services/accounts.ts:120-174`.
- **Defect:**
  - Two reviewers, or one double click, can both pass the `status === "submitted"` check. One possible result is a business marked rejected that still holds a live bank account.
  - Provisioning the same branch twice makes the losing `VirtualAccount.create` throw a duplicate-key error (11000). Its catch block then writes `accountStatus: "failed"` over the winner's `active`, and the retry path never repairs it.
- **Fix:**
  - Use `findOneAndUpdate({_id, status: "submitted", "compliance.status": {$ne: "banned"}}, …)` and return 409 when it comes back null.
  - On 11000, re-read and return the existing account.

### H10. Mobile: sign-out freezes, and the 5-wrong-passcodes wipe can be bypassed (confirmed)
- **Where:** `mobile/src/lib/auth/store.ts:194-212`, `mobile/src/lib/push.ts:115-125`, `mobile/src/lib/auth/session.ts:27` and `:91-118`, and `mobile/src/lib/security/passcode.ts:60-71`.
- **Defect:**
  - `signOut` calls `setUnlocked(false)` first, then `unregisterPush()`. That goes through `api()`, which waits on `whenUnlocked()` and never resolves. This is dormant until `extra.eas.projectId` is set, then every sign-out freezes, including the wipe after too many passcodes.
  - Even without that, the keychain wipe waits on a logout `fetch` with no timeout.
  - `verifyPasscode` still accepts the right code when attempts are already 5 or more.
- **Why it matters:** someone holding the phone can enter the 5th wrong code, force-quit, and repeat. That gives unlimited passcode guesses, and the passcode is the only gate in front of sending money.
- **Fix:**
  - Wipe the refresh token and passcode before any network call.
  - Send the push-token DELETE with a token captured beforehand, or let the server's logout handle it.
  - Put a timeout on the logout fetch.
  - On boot, sign out at once if attempts are 5 or more.

### H11. Web tokens can't be revoked, and web and admin sign-in share one rate limit (confirmed)
- **Where:** `backend/src/services/tokens.ts:19-22`, `backend/src/middleware/auth.ts:21`, `web/src/app/(auth)/actions.ts:110-113`, `web/src/lib/api/client.ts:48-58` and `admin/src/lib/api/client.ts:21-31`.
- **Defect:**
  - The web token lasts 7 days and has no `sid`. Sign-out only deletes the cookie, and "sign out everywhere" leaves web tokens alone.
  - Server actions don't forward the client's IP. Every web sign-in therefore comes from the web server's address and shares one 30-per-15-minute bucket. An attacker can keep every business user (or every staff member) locked out of sign-in.
- **Fix:**
  - Give web sign-ins a server-side session (`sid`) and revoke it on sign-out.
  - Forward the client IP the way `lib/public-pay.ts` does, with the web server listed in `TRUST_PROXY`.
  - Key the auth limits on email plus IP.

### H12. The embed "confirm on your server" guidance doesn't tie a payment to the merchant (confirmed)
- **Where:** `backend/src/services/paymentLinks.ts:147-149` and `docs/briefs/payment-links.md:184`.
- **Defect:** The snippet tells merchants to check only `status === "paid"` and `mode === "live"`, and `clientReference` is set by the payer.
- **Why it matters:** an attacker pays a cheap link they control, using the victim merchant's order id as the reference, and hands that checkout token to the merchant's `onSuccess`.
- **Fix:**
  - Tell merchants to also check the link slug or business id and the amount.
  - Better: give them an authenticated verify endpoint or signed webhooks.

### H13. Transfers and approvals have no server-checked step-up (confirmed, design)
- **Where:** `backend/src/routes/transfers.ts:46-49` and `mobile/src/app/(app)/payments/review.tsx:58-67`.
- **Defect:** The passcode or Face ID check before a send happens only on the phone. A bearer token on its own can send money or approve a transfer.
- **Fix:** add a transaction PIN the server checks, or a signature from a Secure Enclave or Keystore key over a server nonce. The same mechanism would replace the bearer-secret design of biometric sign-in (`backend/src/services/biometricKeys.ts:54-67`).

## Low (worth a ticket)

**Auth**
- Account enumeration: register returns 409 `EMAIL_TAKEN`, and `OTP_COOLDOWN` 429s leak whether an account exists (`controllers/auth.ts:87,112,141`).
- The authenticator can be enrolled or swapped without the password or current code, and `/2fa/*` has no rate limiter (`controllers/auth.ts:201-228`).
- AES-GCM has no `authTagLength` and no AAD (`backend/src/utils/crypto.ts:18-19`).
- The last super admin can be removed if two of them demote each other at the same time (`services/staff.ts:30-41`).

**Public pay**
- `public-pay.ts` forwards the client's raw `X-Forwarded-For`, so payers can spoof their IP if nothing at the edge overwrites it (`web/src/lib/public-pay.ts:8-12`).
- A link taken down for fraud still shows its bank account to open checkouts (`controllers/publicPaymentLinks.ts:54-58`).
- `maxPayments` can be oversold, because pending checkouts aren't counted (`services/paymentLinks.ts:54`).
- `embedOrigin` comes from the request body, so it is advisory only (`controllers/publicPaymentLinks.ts:240-249`).
- The per-IP stream cap doesn't group IPv6 addresses by subnet (`services/linkStream.ts:54-67`).
- Payer name, email and phone go in the iframe query string (`web/public/embed.js:43-50`).

**Money**
- A crash between `transfer.save()` and `recordPayoutTransaction` loses the debit row (`services/transfers.ts:494-495`).
- A failed auto-save is never retried (`services/pockets.ts:226-246`).
- Provider states other than `success` and `failed` (such as reversed or cancelled) are polled forever, and nothing escalates stuck transfers (`services/transfers.ts:548-574`).
- Approval thresholds can be avoided by splitting a transfer, because there is no cumulative limit (`services/approvals.ts:29-36`). This may be a product decision.

**Mobile**
- Deep-link ids go into API paths without encoding (`mobile/src/lib/api/transfers.ts:127,139`, `banking.ts:111`).
- Approval-rule changes have no step-up (`approval-rule.tsx:74`).
- The TOTP secret stays on the clipboard with no expiry.
- In two edge cases a passcode can be set without the password (`lib/security/passcode.ts:46-51`).

**Ops**
- There are no security headers (CSP, HSTS, Referrer-Policy, `frame-ancestors 'none'`) outside `/pay/*` (`web/next.config.ts`, `admin/next.config.ts`).
- `tests/setup.ts` doesn't pin `PUSH_PROVIDER`, `EXPO_ACCESS_TOKEN` or `UPLOAD_DIR`.
- Missing indexes and constraints:
  - `VirtualAccount.accountNumber` has no index, although every recipient lookup queries it.
  - `KybDocument` has no unique index on `(business, type, person)`.
- Audit gaps: opening a KYB document, `resendStaffInvite` and `transactions/sync` aren't audited.

## Done well (leave these alone)

**Auth and sessions**
- JWTs are pinned to HS256 and `typ` is checked on every verify. Staff tokens use their own secret and token types, so business and staff tokens can't be used on each other's routes.
- Device sessions store a hashed refresh token, rotate it on every use and catch a replayed one.
- Staff sessions have idle and absolute expiry, and the role is re-read on every request.
- Passwords use argon2id, and failed logins check against a dummy hash so they take the same time. OTPs are hashed and compared in constant time. Invite tokens are 256-bit and stored hashed.

**Authorization**
- Every business route and admin route has a permission guard, and a test enforces this for admin.
- `X-Business-Id` is checked against the user's membership, and writes never fall back to another business.

**Money**
- Amounts are integer kobo end to end, on every client.
- Payouts use a stored idempotency key, and ambiguous errors aren't treated as failures.
- Approvals and pocket withdrawals use conditional atomic updates.
- Holds and savings are worked out from documents rather than from counters.

**Webhooks**
- Liquifia webhooks are checked with an HMAC over the raw body in constant time, deduped on `(provider, eventId)`, and the payload is never trusted.

**Content handling**
- No NoSQL injection: zod is used everywhere, and Express 5's simple query parser stops operator injection.
- Regex input is escaped and paging is bounded.
- Uploads are re-encoded with sharp, SVGs are rasterised, files are served with `nosniff` and `CSP default-src 'none'`, and KYB uploads are checked by their first bytes (file signature).
- No data is shared between users through caching: every fetch is `no-store`, and there's no `unstable_cache` or `use cache`.

**Compliance**
- The freeze is enforced in depth: a route guard, `assertMoneyCanMove`, and `submitTransfer` holding the transfers of suspended or banned businesses.

**Mobile**
- The access token lives only in memory, and the refresh token is a this-device-only keychain item.
- The biometric vault is tied to the current enrolled biometrics.
- Screen capture is blocked, the app-switcher snapshot is blurred, and release builds require https.

**Test harness**
- The test harness is isolated: fake Liquifia keys, an unreachable live URL, an in-memory Mongo, and a mock that refuses non-local addresses.
